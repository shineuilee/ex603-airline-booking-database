## Modelling Justification

When I designed the relational database for this airline booking project, my main goal was to build a clean structure that keeps the data safe and matches real-world flight operations. My primary design decisions focused on choosing the right primary keys, defining safe delete rules across related tables, and placing strict integrity checks directly inside the database instead of relying only on application code.
For primary keys, I used auto incrementing integer keys for passengers, flights, and bookings. While it is possible to use a passenger's email address or phone number as a primary key, their personal information can be updated at any time. If an email address is used as a primary key and the user changes it, the system has to update every related record across the database, which can lead to slow performance and consistency errors. Using an auto-generated number ID keeps each record stable, never changes over time, and makes joining tables much faster and simpler. For the airports table, however, I decided to use the standard three-letter airport code as a primary key. Airport codes such as IAD, DCA, and BWI are globally recognized, standardized, and mostly permanent, which makes a separate id generation unnecessary. For the flight_routes junction table, I implemented a composite primary key combining flight_id and airport_code. This ensures that an airport cannot accidentally be added to the exact same flight twice.
For referential integrity and ON DELETE rules, I wanted the database to reflect actual airline operational policies. I applied ON DELETE CASCADE to the relationship between flights and flight_routes. If a flight schedule is completely canceled and removed before it ever runs, the individual stops tied to that specific flight have no independent value, so they should be cleaned up automatically to avoid leftover records. On the other hand, I set ON DELETE RESTRICT on all foreign keys connecting to the bookings table. If a customer has already booked and paid for a ticket, the system should prevent anyone from deleting that passenger record or flight record. Deleting these rows would erase critical financial records and official passenger flight list. If a scheduled flight is canceled, the company should update its status flag instead of deleting the row from the database. In the same way, an airport cannot be deleted if active flight routes are still connected to it.
Finally, I decided to enforce critical domain rules at the database level rather than leaving them only to the application. I added check constraints to make sure ticket prices cannot be negative, total seats must be greater than zero, and route points only accept origin, destination, or layover. While front-end forms and server-side code usually validate user input, application software can have bugs, and staff members sometimes update data directly in the database during system maintenance. Enforcing these constraints directly within the database schema ensures that invalid data can never be written, regardless of how it enters the system.


## Reflection

One decision that another designer might have handled differently is how flight routes are structured. Instead of creating a separate flight_routes table, a simpler and common option is to place two columns directly inside the flights table: origin_airport and destination_airport.
Putting both airports directly in the flights table makes sense for simple point-to-point flights. It reduces the number of tables in the schema, and looking up flight info is easy because you can find the route without joining another table. However, I chose to create a separate routes table because real airline operations often include multi-segment flights with layovers, connecting stops, or technical refueling stops. If a database hardcodes origin and destination into the flight table, it cannot handle flights with layovers without changing the schema later.
In terms of everyday use and further usage of this database, using a junction table provides better flexibility. For adding or updating schedules, staff can add, remove, or change a stop without messing with the main flight record. For customer searches, finding every flight arriving at or departing from a specific airport is quick and simple using the routes table. Even though it requires an extra step when joining tables, it handles real flight schedules without running into dead ends.
